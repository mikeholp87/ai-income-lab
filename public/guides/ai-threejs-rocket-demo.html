Quick answer: Start from a source prompt you can read, generate a single-file rocket scene, inspect the HTML preview, then add zoom and rotation. The original prompt is not reproduced here. What I built is a visual coding exercise, not a physics-validated simulator, and the camera controls are the part you can learn from and reuse.

I built a rocket launch scene with GPT-6 Astra from one long prompt, then added camera controls with a follow-up request. The first run took about 23 minutes and produced a single index.html file with the whole Three.js scene inside it. The follow-up for zoom and rotation took a few more minutes.

This guide walks through what I did, what the agent claimed, what I actually checked on screen, and how to add the same kind of mouse camera controls yourself using the documented Three.js addon. It is a visual demo. Nothing here tests whether the rocket behaves like a real one.

Start with a source prompt and a separate project folder

The prompt came from the Bridgebench prompts page, where it is listed as a Three.js rocket launcher alongside other build prompts such as a Minecraft clone and a Mario Kart style game. It is roughly 10,000 characters. It asks for a single HTML file where a Falcon-class booster lifts off with volumetric effects, holds 60 frames per second, and uses a physically based sky and tone-mapped colour. I said in the video that I wasn’t sure what all of that meant, and it didn’t stop the build.

The original prompt is not reproduced here. It lives on that page, and this guide is about the scene and the camera follow-up rather than an exact copy of the prompt.

I pasted it into GPT-6 Astra from my demos folder and asked it to make a new directory first, so the output didn’t land among other projects. I ran it on medium reasoning, which I recommend for most tasks because it balances speed and depth. While it ran I guessed it wouldn’t use more than about 5% of my Pro plan, but I didn’t show the final usage figure, so treat that as a guess rather than a measured cost.

Inspect the generated artifact instead of just the status message

When it finished, Astra reported that the single-file scene was complete, its flight checks passed, 22 sampled frames rendered, the controls worked and the final browser run showed no console errors. It named the file as a Meridian 9 launch page in index.html.

That is the agent’s own report. I didn’t rerun those checks independently, so I treated it as a claim and opened the file. I refreshed the preview to make sure I had the finished version, then went through the controls: restart, audio on and off, a graphics quality setting from high to low, a debug mode, hiding the overlay, replay, pausing with the space bar, 2x speed and an engine illumination toggle that didn’t visibly change much. I could watch the stage separation and the booster falling back down.

I also opened the code. It is all in one HTML file, and I said plainly in the video that I couldn’t make heads or tails of it. That is fine for a demo, but it means anything you want to change later has to go through the agent or through someone who can read Three.js.

Turn a usability gap into one precise follow-up

The first version kept the rocket too far away, and I wanted to look at it up close. So I sent one narrow request: add zoom in and out controls using the mouse wheel. I also said I’d like to rotate with the mouse.

After the update I could click and drag to rotate up, down, left and right around the rocket, zoom out to see the whole launch, and zoom right in on the plume as it lifted off. That one-change, one-check loop is the part worth copying. A request like “make it more realistic” is hard to verify. “Mouse wheel zooms and dragging rotates” is something you can test in ten seconds.

Add orbit controls yourself

I don’t know exactly which camera code Astra wrote, because I didn’t read the file closely. If you want the same behaviour in your own Three.js scene, the standard tool is OrbitControls. Its documentation says it orbits with the left mouse button, zooms with the mouse wheel or middle button, and pans with the right button or arrow keys. It is an addon, so it has to be imported separately from the core library.

In a single HTML file without build tools, the Three.js installation manual uses an import map in the <head> so the browser knows where three and its addons live. Replace <version> with a real three.js version, and import everything from the same version and CDN:

<script type="importmap">
{
  "imports": {
    "three": "https://cdn.jsdelivr.net/npm/three@<version>/build/three.module.js",
    "three/addons/": "https://cdn.jsdelivr.net/npm/three@<version>/examples/jsm/"
  }
}
</script>

Then, in your module script, this is the setup from the OrbitControls docs, using the camera, renderer and scene you already have:

import { OrbitControls } from 'three/addons/controls/OrbitControls.js';

const controls = new OrbitControls( camera, renderer.domElement );

// controls.update() must be called after any manual changes to the camera's transform
camera.position.set( 0, 20, 100 );
controls.update();

function animate() {
  // required if controls.enableDamping or controls.autoRotate are set to true
  controls.update();
  renderer.render( scene, camera );
}

If zooming goes through the rocket or drifts off into empty space, the docs list minDistance and maxDistance to limit how far you can dolly in and out with a perspective camera. The manual also notes that some features don’t work when you double-click an HTML file, and suggests running a local server from the project folder, for example npx serve ., then opening the URL it prints.

Separate prompt requirements from measured outcomes

The prompt asks for 60 frames per second. The scene shows an FPS counter, and on my Lenovo laptop at 1920 by 1080, including full screen, it looked decent. That is one laptop with no comparison, so I can’t promise the same frame rate on other hardware.

The 23 minutes is the same kind of observation: one run, one model setting, one account. Another model, plan or reasoning level could take longer or shorter, and usage depends on the route you run it through.

What remains unfinished

I said on camera that I’d like to add clouds and make it look more realistic, because it isn’t very 3D looking yet. I didn’t build either in the video, so neither is a feature of this demo.

If you repeat the exercise, a sensible finish line is: the scene loads, the controls you asked for respond, and the browser console shows no relevant errors. Check those yourself rather than relying on the agent’s summary. A good-looking launch animation is still not evidence about real rocket physics.

FAQ

Is the exact Bridgebench prompt reproduced?

No. It is about 10,000 characters and lives on the Bridgebench prompts page. This guide covers the scene and the camera-control follow-up instead.

How long did the build take?

About 23 minutes for the first version on GPT-6 Astra medium, then a few more minutes for the zoom and rotation follow-up. That is one run, not a guaranteed time.

Does “single HTML file” mean no dependencies?

Not necessarily. All the code sat in one index.html, but the Three.js installation manual shows single-file pages loading the library from a CDN through an import map, which needs a network connection. Open the file and check its imports before assuming it works offline.

How do I add mouse zoom and rotation to a Three.js scene?

Import OrbitControls from three/addons/controls/OrbitControls.js, create it with your camera and renderer.domElement, and call controls.update() after moving the camera. The wheel zooms and left-drag rotates by default.
