Make.com Google Sheets tutorial: filter approved requests

Quick answer

Create a Make.com scenario that watches new rows in an Intake sheet, filters for Approved = yes, and adds each approved row to a Work queue tab. Run it once on two fictional test rows: the approved one should arrive and the rejected one should not. Keep the schedule off until both checks pass.

Move approved sample requests from an intake sheet to a work queue. This small Make.com project teaches a trigger, a filter, and field mapping with an output you can inspect. 1. Prepare two tabs

If you downloaded the kit, import intake.csv and work-queue.csv into separate new tabs using Google Sheets’ File → Import, then rename the tabs as shown below. Use Insert new sheet(s) so you keep both tabs. Keep expected-first-run.csv for comparison only; do not import it into Work queue.

Create a spreadsheet with tabs named Intake and Work queue. Give both the same first-row headers: Request ID, Task, and Approved. In Intake, add these rows directly below the headers, without blank rows:

Request IDTaskApproved
TEST-001Draft a project briefyes
TEST-002Review an ideano

Leave Work queue empty apart from its headers. No customer details, emails, or external notifications are needed for this exercise.

2. Watch the intake rows

To use the blueprint, create a new, empty scenario and choose Import blueprint from the editor’s three-dot menu. Select approved-requests.blueprint.json. In both modules, connect your Google account and replace YOUR_TEST_SPREADSHEET_ID with your test spreadsheet’s ID from its URL. Review the tab names, field mappings and filter before running. Make’s blueprint instructions explain importing into a new scenario. To build it manually instead, follow these steps.

Create a scenario and select Google Sheets → Watch New Rows. Connect the Google account that owns the test sheet. Select the spreadsheet and Intake tab, enable headers, use header range A1:C1, and set the limit to 2.

For this new test sheet, select All when choosing where to start. That includes the two sample records. Save the module and the scenario. Make’s trigger setup guide explains the starting position and how polling remembers processed rows.

3. Map the destination

Map fields before adding conditions

Add Google Sheets → Add a Row and choose Work queue as its destination. Map each destination column to the corresponding output field from Watch New Rows. Select Raw for the value input option so values are stored as supplied. Choose Insert rows if that option is shown.

The Google Sheets module reference documents the fields and notes that a blank row can stop Watch New Rows from processing later rows.

4. Pass only approved requests

Add a filter on the connection between the modules. Label it Approved requests. Use the trigger’s Approved field, the text equality operator, and the value yes. The destination should receive only rows that satisfy this condition. In Make, clicking the line between two modules opens the panel where you name the filter and set its conditions; each condition has one or two operands and an operator.

5. Run and verify

Save, select Run once, and inspect the module results and the Work queue tab. These are expected results to verify in your own account, not a claim that this scenario has been run on your behalf:

  • TEST-001 appears once in Work queue with the same task and approval value.
  • TEST-002 does not appear because its Approved value is no.
  • A second run with no newly appended intake rows should add no rows.
  • Append TEST-003 with a new task and Approved set to yes; the next run should add that row.

Understand the limits before scheduling

This is an append-only exercise. Watch New Rows is not an approval-update trigger: changing an already processed row from no to yes will not make it a new row. For a real approval queue, design an update-aware workflow or search for pending records on a schedule.

The trigger cursor also does not guarantee exactly-once delivery. Resetting the starting position, copying records, or retrying a partially completed run can produce duplicates. Before using real requests, decide how a stable request ID will prevent repeated processing and how failed runs will be reviewed.

If nothing arrives, check the selected tabs, starting position, header mapping, filter value, and blank rows. If every row arrives, check that the filter is on the route to Add a Row. After the expected results pass, choose a schedule appropriate for your account’s limits and monitor its run history.

A later project could draft a summary for each accepted request. First establish that the right input reaches the right destination. The HeyGen course companion shows how provider IDs and API limits can interrupt a larger Make workflow. For API fundamentals, use the local request exercise.

FAQ

What does this Make.com scenario do?

It watches new rows in an Intake sheet, filters for Approved = yes, and adds each approved row to a Work queue tab.

How do I know the scenario works?

Run it once on two fictional rows. TEST-001 should appear once in Work queue, TEST-002 should not, and a second run with no new rows should add nothing.

Why wasn’t a row I changed to yes copied?

Watch New Rows only sees newly appended rows. Changing an already processed row from no to yes does not make it a new row, so a real approval queue needs an update-aware design.

When should I turn on the schedule?

Only after the expected results pass. Scenario runs use your account’s allowance, so pick a schedule that fits your plan and monitor the run history.
